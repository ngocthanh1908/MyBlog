## Findings

### Medium: password change does not invalidate existing sessions
`changeAdminPassword` only writes a new hash row; nothing increments a token
version or revokes outstanding JWTs. `signAccessToken`/`signRefreshToken`
(`src/lib/auth-utils.ts`) sign only `{ admin: true, type }` with no
password-derived claim, so an access token issued before a password change
remains valid for its full 15-minute lifetime, and a refresh token remains
valid for its full 7-day lifetime, after the admin changes the password. If
the motivation for changing the password is a suspected leaked token/session,
this feature does not actually revoke attacker access — only a code
inspection makes that limitation visible to the admin. Not called out in the
plan's acceptance criteria, so not strictly a scope violation, but it is a
reasonable expectation for a "change password" feature and should be a
conscious decision, not a gap. Mitigations (any one): rotate `JWT_SECRET` on
change (would also log out the admin's active session, rough for single-admin
UX), embed a version/timestamp (e.g. `updated_at` from `admin_credentials`)
in the JWT payload and check it in `verifyToken`/`getAuthFromRequest`, or
explicitly document this as an accepted limitation for a single-admin blog.

### Low/Informational: scrypt cost parameters are Node defaults, not explicitly tuned
`crypto.scryptSync(password, salt, 64)` is called with no `options` argument,
so it uses Node's default N=16384, r=8, p=1. That is a reasonable floor but
on the low end of current guidance for standalone password hashing (OWASP's
current scrypt guidance is N=2^17 with r=8, p=1 for interactive logins, scaled
down for cost). Not a regression — the previous scheme was plaintext env-var
comparison with no hashing at all, so this is a strict improvement — but worth
a conscious call now rather than revisiting later when it's harder to change
without a re-hash migration path. No action required unless the user wants to
tighten it.

### Informational: rate-limit key is client-supplied `x-forwarded-for`
`checkRateLimit(ip, "change-password", 5, 60)` derives `ip` from
`request.headers.get("x-forwarded-for")`, which is attacker-controlled unless
the deployment is behind a trusted proxy that strips/overwrites it. This is
not a regression — `src/app/api/auth/route.ts`'s existing login rate limit
uses the exact same pattern — so it's a pre-existing characteristic of the
codebase, not a defect introduced by this diff. Flagging only because the
task asked specifically about rate-limiting correctness; no action recommended
unless the user wants to harden the login path too, which is out of scope here.

### No issues found on the specifically requested checks
1. **Timing-safe comparison, scrypt path**: `timingSafeStringEqual` is used
   for both the scrypt-hash comparison (`verifyAdminPassword`'s DB-row branch)
   and the plaintext env-var fallback. The length-mismatch early return before
   `crypto.timingSafeEqual` is unchanged from the original code's behavior
   (same early-return-on-length-mismatch pattern existed before this diff) and
   is a non-issue for the hash path specifically, since both sides are always
   128-char hex strings (64-byte scrypt output) when generated by this same
   code — lengths will only ever differ if the DB row is corrupted/foreign
   data, in which case leaking "lengths differ" in near-zero time is not a
   meaningful oracle (the attacker already doesn't control the stored hash).
2. **Scrypt usage**: random 16-byte salt per `changeAdminPassword` call via
   `crypto.randomBytes`, fixed 64-byte derived key, hex-encoded consistently
   on both write and compare (`hashPassword` used symmetrically) — no
   different-length-buffer throw/short-circuit risk in practice (see above).
   Cost parameters are Node defaults — see Low finding above.
3. **Change-password endpoint**: `requireAuth(request)` is called first and
   throws/returns before any DB read/write (verified directly in
   `route.ts:10-14`, consistent with every other protected route in the repo
   — `upload`, `uploads`, `tags`, `posts`). Rate limiting is applied via
   `checkRateLimit` before processing the body. `currentPassword` is verified
   server-side via `verifyAdminPassword` — never trusted from the client.
   `newPassword.length >= 8` is validated server-side (`MIN_NEW_PASSWORD_LENGTH`),
   independent of the client-side `minLength` attribute, which is correctly
   treated as UX-only.
4. **SQL injection**: `getAdminCredentials`/`setAdminCredentials` both use
   `better-sqlite3` prepared statements with `?` parameter binding, matching
   the existing `posts`/`rate_limits` pattern in `db.ts`. No string
   interpolation into SQL anywhere in the diff.
5. **Backward-compat login path**: `hasConfiguredAdminPassword()` preserves
   the original 500 "Server misconfigured" semantics (true if either a DB row
   or `ADMIN_PASSWORD` env var exists), and `verifyAdminPassword` falls
   through to the original timing-safe plaintext-env comparison when no DB
   row exists yet, byte-for-byte equivalent to the pre-diff logic. Confirmed
   by the test "falls back to ADMIN_PASSWORD env var when no DB row exists"
   and the end-to-end old/new password test.
6. **Secret/data exposure**: no `console.log`/`console.error`/`console.warn`
   of password, hash, or salt values anywhere in the new/modified files. The
   change-password endpoint response is `{ success: true }` only — no hash,
   salt, or password echoed back. The login endpoint's response shape is
   unchanged (not touched beyond the password-check line).
7. **DRY**: `verifyAdminPassword` is genuinely shared between
   `src/app/api/auth/route.ts` (login) and
   `src/app/api/auth/change-password/route.ts` (current-password check),
   eliminating what would otherwise be duplicated hash/env comparison logic.
   No parallel reimplementation introduced.
